# GrowRoll — 온라인 멀티플레이 "굴려라 괴혼" 클론 설계 문서

> 목표: 브라우저에서 여러 명이 함께 덩어리(Katamari)를 굴려 물건을 붙이며 키우는 실시간 3D 멀티플레이 게임.
> 프론트엔드는 **Vercel**, 게임 서버는 **무료 상시 가동 호스팅**에 배포.

---

## 1. 게임 개요 (무엇을 만드는가)

"굴려라 괴혼(Katamari Damacy)"의 핵심 루프:

1. 플레이어는 끈적한 공(**덩어리, Katamari**)을 굴린다.
2. 덩어리보다 **작은 물체**에 부딪히면 그 물체가 공에 **붙어서** 공이 커진다.
3. 공이 커지면 더 큰 물체도 붙일 수 있다 (계단식 성장).
4. 제한 시간 내에 **가장 크게 키우는** 것이 목표.

### 멀티플레이 변형 (GrowRoll 고유 규칙)
- **동일 맵**에서 여러 플레이어가 동시에 각자의 덩어리를 굴린다.
- 같은 오브젝트를 두고 **경쟁** (먼저 닿은 사람이 획득).
- (선택) 상대보다 충분히 크면 **상대 덩어리를 통째로 흡수** 가능 → 긴장감.
- 라운드(예: 3~5분) 종료 시 가장 큰 덩어리가 승리.

### 모드 (로드맵 순서)
1. **싱글 프로토타입** — 물리/성장/붙이기 검증 (오프라인)
2. **협동/경쟁 룸** — 2~8인 같은 맵
3. (선택) 팀전, 랭킹, 관전

## 2. 기술 스택 결정 및 근거

### 2.1 렌더링 / 물리 (성능 우선 추천)

**결정: Three.js (코어) + Rapier(@dimforge/rapier3d) 물리엔진**

| 후보 | 성능 | DX | 판단 |
|---|---|---|---|
| **Three.js + Rapier** | ★★★★★ | ★★★☆☆ | **채택.** 렌더 루프·인스턴싱·컬링을 직접 최적화 가능. Rapier(Rust→WASM)는 결정적(deterministic) 옵션과 뛰어난 성능 제공 |
| React Three Fiber + Rapier | ★★★★☆ | ★★★★★ | React 친화적이나 수천 개 오브젝트에서 리렌더 오버헤드 주의 |
| Babylon.js | ★★★★☆ | ★★★★☆ | 올인원. 하지만 물리 결정성/서버 공유엔 Rapier가 유리 |

**Rapier를 고른 핵심 이유**: Katamari는 서버·클라이언트가 **같은 물리 결과**를 내야 치팅·불일치가 적다. Rapier는 **JS(WASM)와 Rust 동일 엔진**이라 서버(Node)와 클라이언트(브라우저)가 완전히 같은 물리를 돌릴 수 있고, **deterministic 모드**를 지원한다.

**성능 전략 (Katamari 특유의 문제 = 붙는 오브젝트가 수백~수천 개)**:
- 월드 오브젝트는 `InstancedMesh`로 배칭 렌더.
- **붙은 오브젝트는 물리 콜라이더에서 제거**하고, 덩어리의 콜라이더 반지름만 키운다. (수천 개 콜라이더를 유지하지 않음)
- 붙은 오브젝트의 **시각 메시는 덩어리에 부모-자식으로 고정**하거나, 멀리 있으면 LOD/머지.
- 프러스텀 컬링, 오브젝트 풀링, 원거리 오브젝트 스폰/디스폰(청크 스트리밍).

### 2.2 프론트엔드 앱

**결정: Vite + TypeScript (SPA)**, UI는 최소한의 React (로비/HUD).
- 게임 캔버스는 순수 Three.js 렌더 루프, 로비/설정/HUD만 React.
- Vercel에 정적 배포 (SPA). → 빠르고 무료.

### 2.3 서버 (게임 로직)

**결정: Node.js + TypeScript, WebSocket(ws 라이브러리) 기반 authoritative 서버.**
- 서버가 물리(Rapier)를 **권위적으로(authoritative)** 시뮬레이션하고, 클라이언트는 입력만 전송 + 결과를 보간(interpolation)해 렌더.
- 이유: 공정성(누가 먼저 오브젝트를 먹었는가), 치팅 방지, 상태 일관성.

## 3. 호스팅 서버 추천 (멀티플레이·무료)

### 요구사항
- **상시 가동** (콜드스타트 = 게임 중 끊김 → 치명적)
- **WebSocket** 지원 (양방향 실시간)
- **일정한 CPU** (30~60Hz 물리 틱을 지속적으로 돌려야 함)

### 비교

| 호스트 | 상시가동 | WS | 지속 CPU 루프 | 무료 한도 | 총평 |
|---|---|---|---|---|---|
| **Oracle Cloud Always Free** | ✅ | ✅ | ✅ 완전한 VM | ARM Ampere 4 vCPU / 24GB, 항상 무료 | **성능 최강**. 단, 계정 승인·서버 운영 직접 |
| **Fly.io** | ✅(min 1 유지) | ✅ 친화적 | ✅ | 소규모 무료 allowance | **DX 최고**, 글로벌 엣지로 지연 낮음 |
| **Cloudflare Durable Objects / PartyKit** | ✅(요청시 즉시) | ✅ 룸 단위 최적 | △ CPU/wall-time 제한 | 넉넉 | 룸 매치메이킹엔 최고, **고빈도 물리 루프엔 제약** |
| Render 무료 | ❌ 15분 후 잠듦 | ✅ | ❌ | — | **게임엔 비추천** (콜드스타트) |
| Railway | ✅ | ✅ | ✅ | 사실상 유료 전환 | 무료 조건 좁음 |

### 최종 결정: **Oracle Cloud Always Free VM** ✅

- **ARM Ampere A1 인스턴스 (최대 4 vCPU / 24GB RAM)** 가 **영구 무료**.
- **항상 켜짐 → 콜드스타트 없음** (게임 서버에 결정적으로 유리).
- 완전한 VM이므로 30~60Hz authoritative 물리 루프를 제약 없이 실행.
- 트래픽이 커져도 무료 한도 내에서 버틸 수 있음.
- 트레이드오프: 계정 승인, 방화벽/포트 개방, 배포 파이프라인을 **직접 구성**해야 함 → `docs/DEPLOY-ORACLE.md` 가이드 제공.

**배포 방식**: 서버를 **Docker 컨테이너**로 패키징하여 Oracle VM에서 실행. (컨테이너 기준이라 추후 Fly.io/다른 호스트로도 그대로 이전 가능.)

#### 참고용 대안 (지금은 미채택)
- **Fly.io**: DX가 가장 좋음(`fly deploy` 한 줄). 나중에 이전이 필요하면 Docker 이미지 그대로 사용 가능.
- **Cloudflare Durable Objects / PartyKit**: 룸 매치메이킹이 커지면 "물리는 Oracle, 매치메이킹만 Cloudflare" 하이브리드로 확장 가능.

## 4. 네트워킹 아키텍처 (넷코드)

### 모델: **서버 권위 + 클라이언트 예측 + 보간**
```
[클라이언트]                         [게임 서버 (Fly/Oracle)]
 입력(WASD/마우스) ──────────────▶  입력 수신 → Rapier 물리 시뮬(권위)
 로컬 예측(즉시 반응)                 30Hz로 스냅샷 브로드캐스트
 서버 스냅샷 수신 ◀────────────────  { 각 플레이어 위치/회전/크기, 남은 오브젝트 }
 원격 플레이어 = 보간(interpolation)
 로컬 플레이어 = 예측 + 서버 보정(reconciliation)
```

- **틱레이트**: 서버 물리 30~60Hz, 네트워크 스냅샷 15~30Hz.
- **전송 최적화**: 스냅샷은 **델타 압축** + 이진 직렬화(예: MessagePack/flatbuffers). JSON은 프로토타입까지만.
- **관심 영역(AOI)**: 큰 맵이면 근처 오브젝트/플레이어만 전송.

### 메시지 프로토콜 (초안, `packages/shared`에서 공유)
- Client→Server: `join`, `input`(이동/카메라), `ping`
- Server→Client: `welcome`(내 id, 맵 시드), `snapshot`(엔티티 상태 델타), `pickup`(오브젝트 획득 이벤트), `roundEnd`(결과)

## 6. 핵심 게임플레이 시스템

1. **이동/조작**: 괴혼 특유의 "두 스틱(양손)" 조작 → 키보드는 WASD + 마우스, 모바일은 가상 스틱. 물리적으로 공에 힘/토크 적용.
2. **성장/붙이기 규칙**:
   - 접촉 오브젝트의 `size <= katamari.radius * PICKUP_RATIO`이면 획득.
   - 획득 시 `katamari.volume += object.volume` → 반지름 재계산(`r = (3V/4π)^(1/3)`).
   - 붙은 오브젝트는 물리 콜라이더 제거, 시각 메시만 덩어리에 부착.
3. **카메라**: 덩어리 크기에 따라 줌아웃(스케일 감각).
4. **월드**: 시드 기반 절차적 배치 또는 고정 레벨 + 오브젝트 크기 티어(1cm~수십 m).
5. **승패/점수**: 라운드 타이머, 최종 반지름 비교.

## 7. 성능 예산 (목표)
- 클라이언트 60 FPS 유지 (오브젝트 5,000개 규모 맵 기준).

- 서버 틱: 8인 룸 기준 물리 스텝 ≤ 5ms/tick.

## 10. 확정된 스택 요약
- **클라이언트**: Vite + TypeScript + **Three.js + Rapier** → **Vercel** 배포
- **서버**: Node + TypeScript + ws + Rapier (authoritative) → **Oracle Cloud Always Free VM** (Docker)
- **공유**: `@growroll/shared` (프로토콜/상수), pnpm workspaces 모노레포
